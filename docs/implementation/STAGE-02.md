# Stage 02 — Backend contracts and clean world

## Result

Stage 02 is implemented on `codex/backend-stage-02`, created from `main` at `66f0c2adaf9e2cc5b4391978a699bda6a24ecdbd`. It compiles the source-locked LL01 world package, defines shared simulation/client contracts, and initializes a deterministic clean T0 save. The work does not change or merge the `frontend/demo-ui-v0` branch.

The implementation starts with three enabled server capabilities: clean-start initialization, inspection of entities already known to the player, and projection of a privacy-filtered player view. Registered gameplay commands outside those capabilities return stable disabled reason codes. No persistence adapter or gameplay settlement for later stages is included.

## Source authority and compilation

- `packages/content/src/sourceLock.ts` pins the exact source main commit, release IDs, SHA-256 for each source input, content version, ruleset version, and a read-only frontend reference.
- `packages/content/src/compiler.ts` verifies source and fixed-table hashes before parsing. It compiles 38 sites, 41 cache centers, 10 player anchors, 192 fixed chest instances, 15 hero lairs, 693 fixed lair unit identities, 13 fixed actors, five ecology records, fixed resources/routes, 18 dormant quest IDs, and 30 scheduled timeline rows.
- The generated package keeps the 96 km active-map boundary and original source Z values. XY coordinates are converted from source km to integer millimetres. Chest/cache coordinates and chest loot commitments are fixed; no procedural chest reroll is used.
- The content manifest records source authority classes and conversion decisions. The event source catalog and structure catalog are retained as research-only evidence. The reconciled timeline v0.6 is the selected 30-row schedule; the legacy File 01 schedule is not loaded alongside it.
- Runtime content is generated by `npm run content:compile` into `packages/content/generated/` and checked against its content hashes when loaded.

## Clean T0 state and player view

`createNewGame` validates package/ruleset/content versions and constructs Lí Lan's File 06 T0 state: level 1, 0 XP, exact attributes and SSS talent, 236/236 mana, sealed career payload, H0 territory, damaged house, active level 1 fire, and level 1 tomb with 20/20 Death Qi and an empty queue. The fire keeps its documented radius and temperature range; its exact remaining fuel is `null` with `state_unobserved` knowledge. Opening protection remains pending the later authoritative time settlement.

The start has two unobserved inventory containers. The 40-slot territory supply contains the source-defined bread, pot, axes, hammers, staff, and shield. The carried food bag is derived from the locked hash/rejection-sampling contract and stores a commitment and draw count. Neither inventory nor the sealed career payload is exposed in the initial player view. Six source-defined corpses are represented at T0 as unobserved, with no ownership. All field chests start unopened, all questlines dormant, all 30 calendar rows scheduled with no settlement receipts, and no player-owned units, active jobs, currency, exploration, or prior progress.

The view exposes the known H0 site and documented fire overlay, while hiding unknown sites, caches, lairs, actors, corpses, sealed career details, and unobserved supplies. The fixed world remains loaded independently of player knowledge.

## Contracts and command boundary

`packages/contracts/src/index.ts` defines shared world, save, event, receipt, command, and player-view types. Command envelopes are discriminated by command type. Runtime validation rejects unknown envelope/payload fields, malformed entity references, unsupported command values, and client-supplied authoritative results such as inventory, rewards, damage, XP, or time advancement.

Only inspection of an already-known entity mutates state in this stage. It increments the revision, emits one event, and records an idempotent receipt. Reusing the same command ID with a different request is rejected. Unknown entities and unsupported gameplay commands are rejected without applying client state.

## Frontend boundary and follow-up

The frontend branch and its demo client were read only to understand the client-facing shape. No frontend source, fixture, or branch was changed. A frontend fixture adapter is deliberately left for a separately authorized integration step; Stage 02 does not assume or edit that branch.

Next, Stage 03 can add persistence against these contracts. Later stages can implement authoritative time settlement (including EV00 protection), container/career interactions, spatial discovery, resource ledgers, construction, revival/combat, and trade. Their commands already have explicit disabled reasons. The remaining fuel amount, and research-catalog candidates without runtime authority, stay unresolved rather than receiving invented state.

## Validation

```text
npm run content:compile
Compiled 38 sites, 192 chests, 15 lairs, 693 fixed lair units and 30 scheduled events.

npm run test:stage02
9 tests passed; 0 failed.
```

The tests cover source locks and world counts, coordinate and chest commitments, lair/population conservation, hash and bag golden vectors, deterministic clean initialization, privacy filtering, command validation/receipts, clock conversion, and fail-closed source hash checks. A separate TypeScript static typecheck was unavailable in the offline environment because no TypeScript compiler or type packages are installed; runtime execution uses Node 24's `--experimental-strip-types`.
